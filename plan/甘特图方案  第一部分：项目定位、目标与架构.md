# XGantt 通用甘特图组件开发任务

## 一、你的角色与工作方式

你是一名具备成熟商业组件库开发经验的高级前端架构师，同时熟悉项目管理系统、ERP、生产资源排程、时间轴可视化、复杂交互和大数据量前端性能优化。

本次任务是在现有项目中设计并开发一个高质量、可复用的甘特图组件 `XGantt`。

使用目标驱动型开发方式。

**核心原则：明确目标、保证结果、允许自主选择最合适的实现方案。**

你应主动检查项目现状、分析需求、制定合理架构、编写代码、运行验证并修复问题。

不要机械地按照未经验证的技术假设实施，也不要仅停留在方案讨论阶段。

当某项技术方案存在更优替代方案时，可以自行调整，但必须说明重要的取舍。

对于已经明确的需求，不需要反复征求确认。只有涉及重大兼容性风险、不可逆修改或者无法合理确定的业务规则时才需要询问。

## 二、项目背景

### 2.1 技术环境

项目是一个自研的 Vue 组件库。

主要技术环境：

- Vue 3
- TypeScript
- Vite
- pnpm
- 现有自研组件库 x.ui
- 现有组件包括 XLayout、XForm、XTable、RemoteTable、Bricks 等
- 主要品牌色为 `#0b806a`
- 主要开发环境为 Windows，VSCode

以上属于背景信息，不代表可以假设仓库当前的目录结构或具体配置。

开始开发前，必须检查真实项目，确认：

1. 项目目录结构。
2. Vue、TypeScript、构建工具及相关依赖版本。
3. 组件命名、组织和导出约定。
4. 现有主题系统、CSS 变量、明暗主题和样式规范。
5. 图标、弹出层、菜单、Tooltip、表格等可复用能力。
6. 现有组件的 Props、Events、Slots、Expose 风格。
7. 现有示例、文档、测试及构建机制。
8. 项目是否已经包含可复用的虚拟滚动或拖动能力。

应尽可能复用已有基础设施，保持整个组件库体验统一。

禁止为了实现甘特图随意引入一套与现有 UI 风格冲突的组件系统。

### 2.2 开发定位

`XGantt` 不是一次性业务页面，而是组件库内可以长期维护的基础组件。

必须同时考虑以下业务：

**场景 A：项目任务管理**

- 项目任务计划
- 多级子任务
- 开始和结束日期
- 任务完成进度
- 任务依赖关系
- 里程碑
- 实际进度与计划对比
- 项目整体时间安排

**场景 B：ERP 资源排程**

- 员工工作安排
- 设备占用计划
- 生产线排程
- 订单生产周期
- 工序时间安排
- 同一资源上的多个任务
- 不同资源之间的时间冲突
- 资源利用情况

**场景 C：通用时间轴展示**

- 设备状态时间线
- 业务事件周期
- 订单执行时间
- 系统运行记录
- 其他以时间范围和行数据为核心的业务场景

以上场景不要求第一阶段实现所有高级功能，但架构必须支持未来扩展。

## 三、总体开发目标

最终交付一个具有成熟商业组件品质的甘特图。

### 3.1 功能目标

组件应支持：

1. 左侧树形数据表格。
2. 右侧交互式时间轴。
3. 两侧纵向滚动严格同步。
4. 日期刻度缩放与切换。
5. 任务条绘制和编辑。
6. 任务的拖动、缩放和进度调整。
7. 多层级任务展开与折叠。
8. 任务依赖关系。
9. 里程碑显示。
10. 工作日与非工作日显示。
11. 今天线与指定日期定位。
12. 自定义列、样式、任务条和交互。
13. 数据更新与异步保存。
14. 大数据量下保持可接受的流畅度。
15. 只读和权限控制。
16. 支持资源排程的底层扩展机制。

### 3.2 产品体验目标

最终组件不能只是“能够显示任务的 SVG 图”。

它应该具有专业软件应有的交互体验：

- 布局清晰。
- 信息密度适中。
- 拖动顺畅。
- 滚动稳定。
- 缩放自然。
- 日期准确。
- 操作反馈及时。
- 可以快速定位任务。
- 交互不会误操作。
- 用户能够理解每个任务条所代表的信息。
- 鼠标操作具有明确的视觉反馈。
- 复杂数据不会导致整个界面卡顿。

优先保证功能正确性、操作体验和架构稳定性。

视觉细节同样重要，但不能以牺牲交互性能为代价。

## 四、总体架构要求

### 4.1 推荐架构方向

建议将组件分为以下逻辑层：

**第一层：对外组件接口**

负责：

- Props
- Events
- Slots
- v-model
- 暴露的方法
- 与外部业务通信

**第二层：布局与渲染**

负责：

- 左侧任务树
- 右侧时间轴
- 任务条
- 时间刻度
- 依赖连线
- 背景网格
- 拖动反馈
- 提示框
- 滚动与可视区域

**第三层：通用甘特图核心**

负责：

- 时间与像素坐标转换
- 可见任务行计算
- 任务层级关系
- 时间范围管理
- 布局尺寸计算
- 命中检测
- 拖动约束
- 缩放与滚动定位
- 数据索引及缓存

**第四层：调度与业务规则**

负责：

- 任务依赖验证
- 工作日计算
- 日历规则
- 资源冲突判断
- 自动排程
- 关键路径等高级能力

调度与业务规则不应该强耦合在 Vue 的视图组件中。

它们应尽可能设计为可独立测试的 TypeScript 模块。

### 4.2 时间轴内核复用

应考虑抽象独立的时间轴基础能力。

长期目标是让以下组件共享底层能力：

- `XTimeline`
- `XGantt`
- `XResourceGantt`

但不要求它们完全共享同一套视图布局。

例如，项目管理甘特图的左侧是任务树，而资源甘特图的左侧可能是人员、设备、产线分组。

两者应该共享时间刻度、坐标系统、缩放、滚动和时间计算等能力，而不是强行把所有业务布局混合在一个组件中。

是否需要立即公开 `XTimeline`，由你检查现有项目后判断。

避免为了抽象而抽象，也不要把未来明显需要复用的核心算法直接写死在视图组件中。

### 4.3 渲染技术选择

允许合理组合：

- Vue DOM
- CSS
- SVG
- Canvas
- 虚拟滚动

自行根据数据规模、交互复杂度、可维护性和性能评估最佳组合。

重点要求：

- 任务条能够精确交互。
- 时间网格高效渲染。
- 依赖连线可维护。
- 大数据量时只渲染必要区域。
- 不依赖大量无意义的 DOM 更新。
- 缩放、拖动时避免频繁全量重新布局。

不要求所有图形使用单一技术绘制。

### 4.4 依赖要求

优先使用项目现有依赖与基础能力。

可以引入成熟、轻量且维护状态良好的辅助库，但应说明：

- 为什么需要它。
- 它解决什么问题。
- 是否存在更轻的方案。
- 对组件包体积的影响。
- License 是否适合组件库分发。

原则上不要直接将大型第三方甘特图整体封装为 `XGantt`。

本次主要目标是实现具有独立能力、可长期维护、符合 x.ui 设计体系的自研组件。

## 五、架构验收标准

架构至少应满足：

- 业务任务对象与图形布局对象分离。
- 时间计算不依赖具体 Vue 组件实例。
- 任务树数据与可见行数据分离。
- 左右区域使用一致的可见行布局。
- 项目任务视图和未来资源排程视图可复用核心时间能力。
- 组件外部可通过 API 控制主要功能。
- 未使用的高级模块不应成为基础显示能力的强制依赖。
- 不破坏 x.ui 现有组件及导出约定。
- 核心功能能够通过自动化测试验证。

不要仅给出架构图。

完成合理架构后，应继续实现第一阶段组件，并实际验证可用性。
