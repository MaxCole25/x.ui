## 十三、性能要求

### 13.1 性能目标

组件必须面向真实业务使用，而不是仅针对十几个演示任务设计。

至少规划以下数据规模：

- 100 个任务：交互顺畅。
- 1,000 个任务：正常使用，无明显卡顿。
- 10,000 个任务：通过虚拟化等方式保持可用。

需要区分总数据量与当前可见任务量。

以上数据量是设计与验证目标，不代表可以在未经实际测试的情况下声称已经达到。

第一阶段至少建立 100 和 1,000 任务的性能验证场景。

对于 10,000 任务，需制定可执行的性能测试方式，并在相关优化完成后验证。

### 13.2 虚拟化

根据实际情况设计：

- 纵向任务行虚拟化。
- 横向时间范围虚拟化。
- 可视区域缓冲。
- 大量依赖连线的可见性判断。
- 非可见任务的渲染控制。

关键要求：

虚拟滚动不能造成左右任务行错位。

展开折叠后，必须正确更新可见数据。

横向滚动时，时间刻度、任务条、依赖线和背景网格必须保持一致。

### 13.3 性能优化

重点检查：

- Vue 响应式更新范围。
- 不必要的 computed 重新计算。
- 任务 ID 索引。
- 层级关系缓存。
- 日期坐标换算缓存。
- DOM 节点数量。
- 任务条位置批量计算。
- 滚动中的布局抖动。
- 拖动中的重复重绘。
- SVG 连线数量。
- 大量数据变更时的处理方式。

可以根据需要使用 requestAnimationFrame 等调度手段。

但不要为简单场景引入过度复杂的渲染架构。

### 13.4 操作体验

目标是在常规桌面开发环境中：

- 普通拖动尽量接近 60 FPS。
- 横向滚动不出现明显跳帧。
- 缩放过程不产生大面积闪烁。
- 展开折叠不出现明显错位。
- 不产生持续增长的内存泄漏。

性能结论必须基于实际测试，而不是主观描述。

## 十四、数据正确性与可靠性

### 14.1 数据校验

必须合理处理：

- 空数据。
- 重复任务 ID。
- 无效日期。
- 开始日期晚于结束日期。
- 父级任务不存在。
- 循环层级。
- 无效任务依赖。
- 依赖指向不存在的任务。
- 非法进度数值。
- 缺失的可选字段。
- 大量任务同时更新。

### 14.2 边界规则

需要明确定义：

- 普通任务是否允许零工期。
- 里程碑的日期表示方式。
- 日期与日期时间是否能够混用。
- 进度是否允许超出 0 至 100。
- 任务能否拖出当前可见范围。
- 是否允许跨非工作日。
- 是否允许只读任务被程序更新。
- 父级汇总任务的日期如何计算。
- 父任务的进度是自动计算还是允许手动输入。

对于具有业务差异的规则，应尽可能支持配置。

不要把某个特定 ERP 的约束硬编码到通用组件中。

### 14.3 更新与回滚

外部业务可能通过 HTTP API 保存任务变化。

需要设计合理的更新流程：

1. 用户执行操作。
2. 组件产生预览状态。
3. 执行必要的本地校验。
4. 生成变化数据。
5. 通知外部业务。
6. 外部业务决定提交或拒绝。
7. 组件与最终数据状态保持一致。

支持异步保存失败后的恢复。

不要让组件默认依赖任何具体后端接口。

## 十五、代码质量要求

### 15.1 TypeScript

要求：

- 类型定义准确。
- 尽量避免 any。
- 公共 API 导出类型完整。
- 核心计算函数参数明确。
- 复杂数据结构有必要的注释。
- 避免直接修改 Props。
- 不使用不安全的类型断言掩盖设计问题。

### 15.2 Vue 3

遵循当前项目的 Vue 开发规范。

合理运用：

- Composition API。
- composables。
- computed。
- shallowRef 或其他合理的状态管理机制。
- 生命周期清理。
- 组件拆分。
- 明确的事件边界。

避免：

- 过大的单文件组件。
- 难以追踪的双向状态同步。
- 不必要的深层 watch。
- 直接操作大量 Vue 内部实例。
- 将时间计算与 DOM 操作混杂。
- 在多个组件中重复维护相同状态。

### 15.3 可维护性

要求：

- 目录结构清晰。
- 单一模块职责明确。
- 核心逻辑可测试。
- 配置集中管理。
- 类型可复用。
- 代码风格统一。
- 不复制已有组件库的基础能力。
- 不在多个地方重复实现日期换算。

优先保持代码简洁、稳定和易理解。

不要为了体现架构复杂度而无意义地增加抽象层。

## 十九、实际执行流程

现在请按照以下方式执行，而不只是讨论设计。

### 第一步：检查项目

阅读现有项目，理解组件库的真实实现方式。

确定能够复用的功能，找出关键技术约束。

不要假设所有预期组件或工具已经存在。

### 第二步：形成方案

基于真实项目制定实现方案。

重点确定：

- 组件边界。
- 时间轴核心设计。
- 数据模型。
- 日期规则。
- 滚动同步策略。
- 渲染方式。
- 编辑状态管理。
- 第一阶段的实现路径。

方案应该明确、简洁、可执行。

### 第三步：直接开发

按合理顺序完成第一阶段核心代码。

优先打通：

**数据输入 → 任务树 → 时间坐标 → 时间轴 → 任务条 → 交互编辑 → 数据变更**

再完善视觉效果、扩展接口和性能优化。

不要只搭空组件或生成没有实际业务逻辑的占位文件。

### 第四步：运行验证

使用项目实际提供的命令执行：

- 类型检查。
- 构建。
- 代码质量检查。
- 自动化测试。
- 可执行的演示验证。

如果项目没有某类测试基础设施，应评估采用最小必要方案，而不是声称已经运行不存在的检查。

### 第五步：修复问题

发现错误时，分析原因并修复。

需要重点关注：

- 日期计算错误。
- 任务条错位。
- 滚动不同步。
- 编辑状态丢失。
- 大量不必要的渲染。
- 主题不兼容。
- TypeScript 类型问题。

修复后重新执行相关验证。

### 第六步：检查完成度

对照阶段一功能清单逐项核验。

区分：

- 已完成。
- 部分完成。
- 未实现。
- 已验证。
- 尚未验证。

然后给出开发结果和后续建议。

## 二十、开发行为约束

整个过程中遵循以下约束。

1. 不进行与 XGantt 无关的大规模重构。
2. 不破坏其他 x.ui 组件。

4. 不引入没有必要的大型依赖。
5. 不把具体业务数据库模型硬编码到组件中。

8. 不将演示数据当作组件内部固定数据。

10. 不把尚未实现的能力写成已支持。
11. 不未经验证就宣称高性能。
12. 不跳过能够实际运行的测试和构建。
13. 不在遇到普通技术问题时停止开发并等待用户给出详细解决方案。
14. 不为了完全实现未来阶段而牺牲当前版本稳定性。
15. 不因为当前缺少高级业务规则，就限制核心组件未来的扩展性。

对于存在多种合理实现方式的部分，允许自主选择。

选择依据是正确性、可维护性、性能、用户体验以及与现有项目的一致性。
