## 六、界面布局和视觉设计

### 6.1 整体布局

采用成熟甘特图常见的左右分栏结构。

左侧为任务或资源数据区，右侧为时间轴区。

整体结构：

**顶部工具栏**

- 时间缩放控制。
- 时间视图切换。
- 定位今天。
- 上一个和下一个时间范围。
- 展开或折叠任务。
- 可选的筛选和搜索入口。
- 可选的显示设置。

**左侧数据区**

- 多列表格。
- 任务名称。
- 开始日期。
- 结束日期。
- 工期。
- 完成进度。
- 状态。
- 负责人等自定义字段。

**右侧时间轴区**

- 多层日期表头。
- 时间网格。
- 任务条。
- 完成进度。
- 任务依赖线。
- 里程碑。
- 今天线。
- 非工作日背景。
- 任务选中和悬停状态。

**底部可选区域**

- 水平滚动条。
- 任务统计信息。
- 当前时间范围。

以上元素应支持按需显示。

### 6.2 外观要求

遵循 x.ui 现有设计风格。

主色参考 `#0b806a`，优先接入组件库已有主题变量，不要在组件内部大量硬编码颜色。

要求：

- 支持明暗主题。
- 配色克制。
- 适当圆角。
- 清晰的表格分隔线。
- 合理的选中态、悬停态、禁用态。
- 日期表头具有清楚的层级。
- 非工作日背景应区别于普通工作日。
- 今天线明显但不过于抢眼。
- 进度部分与未完成部分有明确区别。
- 依赖关系线尽量避免视觉混乱。

支持 CSS 变量或其他符合 x.ui 现有规范的主题定制机制。

### 6.3 布局调整

应支持：

- 左侧数据区宽度调整。
- 左侧列宽调整。
- 时间轴水平滚动。
- 整体纵向滚动。
- 固定日期表头。
- 固定左侧列头。
- 左侧任务树展开折叠。
- 任务选中时左右联动高亮。

重点保证：

**同一个任务的左侧表格行和右侧任务条，在任何滚动、展开、折叠、缩放情况下都必须保持严格对齐。**

对于长文本、不同数据状态、任务折叠、虚拟滚动等情况，要有统一的行高和布局策略。

## 七、时间轴设计

### 7.1 时间刻度

目标支持以下刻度：

- 小时
- 天
- 周
- 月
- 季度
- 年

不同刻度下，时间表头应自动使用合理的多层结构。

例如：

日视图：上层月份，下层日期。

周视图：上层月份，下层周范围。

月视图：上层年份，下层月份。

小时视图：上层日期，下层小时。

实际刻度层级和显示格式可以根据可用空间优化。

### 7.2 时间缩放

应支持：

- 工具栏放大。
- 工具栏缩小。
- 切换预设视图。
- 可选鼠标滚轮组合键缩放。
- 程序化设置缩放级别。

缩放时尽量保持当前视觉中心对应的时间不变。

不能每次缩放都无条件跳回时间轴起点。

缩放应该调整日期到像素的映射，而不只是对整个画布执行 CSS transform。

### 7.3 时间定位

对外提供合理的方法：

- 定位今天。
- 定位指定日期。
- 定位指定任务。
- 将任务滚动到可见区域。
- 自动适配所有任务的时间范围。
- 设置时间轴显示范围。

对于没有任务数据的情况，组件仍应正常显示空状态或指定的时间范围。

### 7.4 日期正确性

这是核心要求之一。

必须正确处理：

- 不同月份天数。
- 闰年。
- 跨月任务。
- 跨年任务。
- 周起始日配置。
- 不同区域日期格式。
- 夏令时。
- 日期与具体时间的区别。
- 开始和结束日期边界。
- 非工作日和工作日历。

对于按天计划，建议对外采用用户容易理解的首尾日期包含规则。

例如，10 月 10 日至 10 月 12 日代表三天。

内部可以统一转换为半开时间区间，避免绘制宽度和持续时间产生误差。

对于小时级排程，应使用带有明确时区语义的时间数据。

不要将所有日期简单视为固定 24 小时，也不要依赖不明确的字符串解析。

日期计算规则应独立测试。

## 八、左侧任务数据区

### 8.1 树形任务

支持：

- 根任务。
- 子任务。
- 任意合理层级。
- 展开折叠。
- 当前展开状态控制。
- 父子关系校验。
- 可选任务层级调整。

建议使用稳定的任务 ID 和父级 ID 表示层级关系。

需要避免：

- 循环父子关系。
- 重复 ID。
- 父任务不存在导致异常。
- 节点折叠后时间轴仍显示隐藏任务。

### 8.2 表格列

列配置应具有良好的扩展性。

至少支持：

- 字段名。
- 标题。
- 宽度。
- 最小宽度。
- 对齐方式。
- 是否显示。
- 是否允许调整列宽。
- 自定义单元格。
- 自定义格式化。
- 可选编辑能力。

组件不应该将业务列固定写死。

例如，ERP 用户可能需要显示订单号、设备号、产线、工序、负责人等字段。

### 8.3 编辑方式

应支持合理的任务编辑入口：

- 双击任务。
- 双击单元格。
- 点击任务条。
- 外部控制弹窗或编辑面板。

组件应负责发出明确事件，允许业务方决定使用内置编辑能力还是自定义表单。

不要在基础组件中绑定具体的业务编辑页面。

## 九、任务条与交互

### 9.1 任务条显示

任务条至少支持：

- 开始位置。
- 结束位置。
- 完成进度。
- 自定义颜色。
- 选中状态。
- 悬停状态。
- 只读状态。
- 自定义提示信息。

不同类型任务可以采用不同视觉表现：

- 普通任务。
- 汇总任务。
- 里程碑。
- 已完成任务。
- 延迟任务。
- 禁止编辑任务。

任务颜色的业务含义应可配置，不应与组件内部逻辑强绑定。

### 9.2 拖动任务

当允许编辑时：

拖动任务条主体，改变任务开始和结束时间，同时保持任务持续时间。

拖动左侧控制点，改变开始时间。

拖动右侧控制点，改变结束时间。

拖动进度控制点，改变完成比例。

交互要求：

1. 鼠标按下进入准备状态。
2. 移动超过合理阈值后进入拖动状态。
3. 拖动期间实时预览。
4. 显示预期日期或时间。
5. 根据当前时间刻度执行合理吸附。
6. 鼠标松开后执行校验。
7. 有效操作才发出提交事件。
8. 无效操作恢复原始状态。
9. 支持取消拖动。
10. 支持外部业务拒绝或回滚修改。

拖动过程不要频繁向后端发送保存请求。

应特别处理滚动容器边缘拖动、缩放后的坐标换算和鼠标指针离开任务条等情况。

### 9.3 任务选择

支持：

- 单击选择任务。
- 点击空白区域取消选择。
- 双击任务事件。
- 可选多任务选择。
- 程序化设置选中任务。
- 任务选择状态与左侧表格同步。

需要区分点击、双击、拖动操作，避免误触发。

### 9.4 自定义任务条

通过 Slot 或其他符合 Vue 3 的方式，让外部业务能够自定义任务条内容。

例如：

- 任务名称。
- 负责人。
- 状态图标。
- 百分比。
- 设备名称。
- 延迟标识。
- 自定义 Badge。

自定义能力不能破坏拖动和定位逻辑。

## 十、依赖关系与里程碑

### 10.1 任务依赖

架构应支持：

- FS：完成到开始。
- SS：开始到开始。
- FF：完成到完成。
- SF：开始到完成。

支持依赖偏移量及其明确的时间单位。

依赖关系应作为独立数据管理，而不是嵌入图形坐标。

至少规划以下能力：

- 显示依赖连线。
- 选择依赖关系。
- 删除依赖关系。
- 创建依赖关系。
- 校验无效依赖。
- 检测循环依赖。
- 数据变化后重新计算连线位置。

依赖线应根据任务条位置自动更新。

不能因为拖动任务而出现明显的连线错位。

### 10.2 依赖与自动排程的区别

必须区分：

**依赖关系校验**与**自动调整任务时间**。

它们不是同一个功能。

允许项目只显示依赖关系，而不自动移动后续任务。

自动排程应作为可选能力。

不能在用户不知情的情况下修改其他任务的开始和结束日期。

### 10.3 里程碑

里程碑属于零持续时间事件。

应支持：

- 独立任务类型。
- 菱形或其他明显标识。
- 正确的时间定位。
- 选中和点击。
- 自定义样式。
- 可选依赖连接。

不要通过随意增加一天来伪造里程碑宽度。

## 十一、资源排程扩展

资源排程是后续的重要方向，基础架构需要为其预留能力。

### 11.1 资源视图

左侧可以显示：

- 人员。
- 设备。
- 产线。
- 车间。
- 班组。
- 自定义资源。

右侧显示分配给对应资源的任务时间区间。

### 11.2 多任务占用

同一个资源可能：

- 在不同时间执行多个任务。
- 存在部分时间重叠。
- 在同一时间承担多个任务。
- 被限制为同一时间只能执行一个任务。

组件必须允许不同业务采用不同规则。

不能直接认定任务重叠就是错误。

### 11.3 冲突检查

未来应允许外部提供冲突检测策略。

例如：

- 设备不允许时间重叠。
- 人员允许一定数量的并行任务。
- 某产线只能同时生产一张订单。
- 特定资源存在维护时段。

冲突计算和冲突显示要分离。

冲突显示应支持任务条高亮、提示信息等方式。

### 11.4 扩展要求

现在不要求完整实现生产排程引擎，但应确保：

- 资源视图可以复用时间轴核心。
- 任务不必永久绑定单一资源。
- 数据模型可支持独立的任务资源分配关系。
- 可以添加不同的资源行布局方式。
- 可以扩展工作班次及容量规则。

不要把项目任务树模型当作唯一可能的数据布局。

## 十二、对外 API 设计

### 12.1 设计原则

API 需要符合 Vue 3 和 x.ui 现有组件规范。

应做到：

- 简洁。
- 命名统一。
- TypeScript 类型完整。
- 支持受控状态。
- 支持必要的双向绑定。
- 支持扩展。
- 默认行为合理。
- 向后兼容性良好。

避免因内部实现方便而设计大量难以理解的配置项。

### 12.2 基础数据模型

建议规划以下类型或等价设计：

**GanttTask**

- id
- parentId
- title
- start
- end
- progress
- type
- color
- readonly
- expanded
- 业务扩展数据

**GanttDependency**

- id
- from
- to
- type
- lag

**GanttColumn**

- key
- title
- width
- minWidth
- align
- resizable
- visible
- formatter 等

**GanttResource**

- id
- name
- type
- capacity
- 其他资源扩展信息

**GanttAssignment**

- id
- taskId
- resourceId
- start
- end
- 分配数量或占用比例

实际 TypeScript 定义应由你根据使用场景完善。

需要明确哪些字段必填、哪些字段可选，以及各字段的单位、日期语义和默认值。

### 12.3 Props

建议评估并设计：

- tasks
- dependencies
- columns
- zoom
- startDate
- endDate
- rowHeight
- readonly
- showToday
- showWeekends
- showProgress
- showDependencies
- showToolbar
- selectedTaskId
- locale
- timeZone
- calendar
- theme 相关配置

不必机械地使用上述全部名称，应优先与 x.ui 保持一致。

对于对象类型和回调类型，必须提供准确的 TypeScript 定义。

### 12.4 Events

需要合理规划：

- task-click
- task-dblclick
- task-change
- task-move
- task-resize
- progress-change
- task-select
- dependency-create
- dependency-delete
- zoom-change
- range-change

事件应携带足够的上下文。

例如，任务编辑事件应能获得：

- 任务 ID。
- 原始值。
- 建议的新值。
- 操作类型。
- 必要的上下文。

避免事件之间职责重叠，造成一次拖动触发多次业务保存。

### 12.5 Slots

至少考虑：

- 自定义工具栏。
- 自定义任务条。
- 自定义 Tooltip。
- 自定义左侧单元格。
- 自定义任务行。
- 自定义空状态。
- 自定义右键菜单。
- 自定义里程碑。

应在灵活性与实现复杂度之间取得平衡。

### 12.6 Expose 方法

考虑提供：

- scrollToDate
- scrollToTask
- zoomIn
- zoomOut
- fitToTasks
- expandAll
- collapseAll
- refresh
- getVisibleRange

方法名称以组件库实际规范为准。

这些方法必须有明确的调用时机、输入参数和返回行为。

### 12.7 数据同步

必须明确区分：

- 外部传入数据。
- 组件内部临时编辑状态。
- 用户确认或完成编辑后的数据。
- 后端保存结果。

支持由外部业务管理最终数据状态。

不能未经约定直接修改外部传入对象。

应避免在更新后出现组件状态和业务数据不一致的情况。
